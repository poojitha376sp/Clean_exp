\title{Gates Pass, Code Fails: A Measurement-Validity Study of LLM-as-Judge Test Adequacy for Requirement-to-Test Generation}

\author{
\IEEEauthorblockN{Poojitha J, Arushi Tandon, Brahma Reddy Korraprolu, Y. Raghu Reddy}
\IEEEauthorblockA{Software Engineering Research Center\\
International Institute of Information Technology, Hyderabad\\
Hyderabad, India}

\maketitle

\begin{abstract}
Large language models (LLMs) are increasingly used to turn natural-language software requirements directly into test cases, yet evaluating the result remains unsolved. Text-similarity metrics (BLEU, ROUGE, CodeBLEU) are widely recognized as inadequate; the emerging alternative hands generated tests to a second LLM and asks it to judge correctness. \textbf{This paper asks how much that judge should be trusted.} We construct a three-gate evaluation pipeline (representational suitability (RSS), syntactic validity (SFV), and LLM-judged semantic adequacy with groundedness (FSA+$M_g$)) and use it to benchmark 10 open-weight LLMs generating tests from three real software requirement specifications (496 test suites, 4{,}058 test cases). The benchmark surfaces useful comparative findings: model size does not predict adequacy (Spearman $\rho=-0.015$, $p=0.80$, $n=311$), code-specialized models do not outperform general-purpose ones (Mann-Whitney $p=0.14$), and test-case representation choice has a larger and more consistent effect on adequacy than model identity. \textbf{Our primary contribution, however, is a measurement-validity audit of the pipeline itself}: when we check gate verdicts against real test execution, the LLM-based audit agrees with execution on only 2 of 11 test cases (18\%; 95\% Wilson CI: 5\%--48\%); only 2 of 315 generated tests actually pass on execution for one case study; and 78\% of judged suites (243 of 311) assert at least one concrete value not traceable to the source requirement, including 168 of the 214 suites that cleared the adequacy gate. We conclude that gate-passing, as currently operationalized, is a measurably weak proxy for correctness, and that any LLM-as-judge pipeline needs an explicit, reported, execution-grounded validity check.
\end{abstract}

\section{Introduction}

Software requirements specifications (SRS) describe what a system must do in
natural language~\cite{iso29148}; test cases verify that it does~\cite{iso29119_1}. Turning the first into the
second has always been labour-intensive~\cite{garousi2020nlp,wang2022umtg}, and large language models (LLMs) are
now routinely proposed to automate it, generating unit tests, behavioural
scenarios, or formal test obligations directly from a requirement's text~\cite{wang2024testingsurvey,hou2024llm4se,fan2023llmse}. The
question this raises is not whether LLMs can produce \emph{something} that
looks like a test case; they reliably can. The question is whether what they
produce is the \emph{right} test case for that requirement, and whether we can
tell.

Text-similarity metrics such as BLEU~\cite{papineni2002bleu}, ROUGE~\cite{lin2004rouge}, and CodeBLEU~\cite{ren2020codebleu} answer a different
question than the one that matters: they measure how closely generated text
resembles a reference, not whether the generated test exercises the correct
behaviour, uses an appropriate representation for the kind of requirement it
came from, or asserts values the requirement actually specifies. A test case
can score well on n-gram overlap while testing nothing the requirement cares
about, and score poorly while being a perfectly adequate test phrased
differently from the reference. This is well understood in the LLM-for-testing
literature~\cite{evtikhiev2023bleu,schafer2023empirical,yuan2023chatgpt,siddiq2023empirical,liu2023evalplus,chen2021codex}. The natural response has been to stop
comparing generated-text wording to reference-text wording, and instead hand
the generated test to a second LLM that reads it and judges whether it is
actually correct~\cite{zheng2023judging,liu2023geval,gu2024judgesurvey}.

That response trades one hard-to-trust proxy for another. An LLM judge can be
wrong in ways that are harder to detect than a low BLEU score: it can be
confidently, fluently wrong~\cite{wang2024notfair,panickssery2024selfpref}. This paper's contribution is not another judge,
but a direct measurement of how much a reasonably careful judge-based pipeline
should be trusted~\cite{ralph2018construct,kaner2004metrics}, obtained by building such a pipeline, running it at
benchmark scale, and then checking its verdicts against the one thing that is
not a proxy: whether the generated tests actually execute against, and
agree with, the real implementation.

\textbf{Research Questions.} We organize our investigation around four RQs:
\begin{description}[leftmargin=0pt]
\item[\textbf{RQ1}] Does LLM model size or code specialization predict test-suite adequacy as judged by an LLM-as-judge pipeline?
\item[\textbf{RQ2}] Does test-case representation choice affect LLM-judged adequacy more than model identity?
\item[\textbf{RQ3}] How well do LLM-judge gate-pass rates predict real test execution success against the implementation?
\item[\textbf{RQ4}] To what extent do generated test suites assert concrete values not grounded in the source requirement (hallucination), and can that be detected by the gate pipeline?
\end{description}
\textbf{Contributions.}
\begin{enumerate}
\item A three-gate evaluation framework, comprising Representational
Suitability (RSS), Syntactic Form Validity (SFV), and Functional Semantic
Adequacy with Groundedness (FSA+$M_g$), with closed-loop repair, grounded in a
30-representation taxonomy of test-case forms (Sections~\ref{sec:taxonomy}
to \ref{sec:framework}).
\item A benchmark of 10 open-weight LLMs generating tests from three real SRS
case studies: 496 test suites, 4{,}058 test cases, 29 project$\times$model
pairs, each suite also compared against the real implementation
(Sections~\ref{sec:setup} to \ref{sec:results}).
\item A quantified measurement-validity gap between what the gates report and
what execution against real code shows: three independent checks (audit
agreement, execution pass rate, and representation-choice agreement with an
independent heuristic) all land far below what the gate-pass rates alone would
suggest (Section~\ref{sec:validity}).
\item A recommendation, supported by that gap, that groundedness be reported
and thresholded as its own first-class check rather than folded into a single
blended adequacy score.
\end{enumerate}

\section{Motivation: Why Not Just Score Similarity?}
\label{sec:motivation}

To establish that the problem this paper studies is not a straw man, we
conducted a systematic review of the literature on LLMs applied to software
testing~\cite{kitchenham2007guidelines}. Starting from 1{,}200 preprint sources (63 discarded for having zero
citations) merged with published-venue results, we categorized 1{,}392 papers
into four relevance tiers: 127 core, 501 relevant, 484 tangential, and 280
excluded (709 were preprints, 683 published). Of these, 1{,}315 were
independently screened for inclusion by two of the authors, with a third
author arbitrating disagreements. Inter-rater agreement was moderate
(unweighted Cohen's~\cite{cohen1960kappa} $\kappa=0.5253$, 84.79\% observed agreement, $p<0.0001$,
95\% CI $[0.4702, 0.5805]$) and substantial once near-misses (``maybe''
judgments) are weighted as partial agreement (linear-weighted
$\kappa=0.6187$, quadratic-weighted $\kappa=0.6790$). The final screened
portfolio retained 183 papers (13.9\%).

Inter-rater agreement of $\kappa=0.5253$ is moderate by Landis \& Koch's
scale~\cite{landis1977measurement} and acceptable for an exploratory SLR in a rapidly evolving field; the
linear-weighted $\kappa=0.6790$ reflects that most disagreements were between
\texttt{include} and \texttt{maybe} rather than between \texttt{include} and \texttt{exclude}.
The third-author arbitration resolved 196 disputed papers, 84 of which
changed outcome (52 additional inclusions, 32 additional exclusions). This
process underscores a finding also visible in the retained portfolio. The underlying literature is similarly inconsistent about what evaluating
an LLM-generated test should mean: surface similarity, compilation, line
coverage, and human judgment are all in active use within the same subfield,
rarely cross-validated against one another~\cite{yuan2023chatgpt,schafer2023empirical,siddiq2023empirical,wang2024testingsurvey}.
This motivates treating evaluation methodology itself, rather than any
particular generation technique, as the object of study.

\section{A Taxonomy of Test-Case Representations}
\label{sec:taxonomy}

A requirement's natural test representation depends on what kind of behaviour
it describes~\cite{utting2012taxonomy,ammann2016introduction}: a state-dependent requirement is naturally tested with a finite
state machine or a transition table~\cite{chow1978fsm,lee1996fsm}; a concurrency requirement with an
interaction diagram or a temporal-logic obligation~\cite{briand2002uml,pnueli1977temporal}; a pure business rule with
a decision table~\cite{myers2011art}. Treating \textit{generate a test} as representation-agnostic
discards this structure. To ground Gate 1 (Section~\ref{sec:framework}) in
something more principled than intuition, we conducted a second, separate
systematic review targeted specifically at the test-case representation
literature: 412 candidate papers (185 IEEE Xplore, 112 ACM Digital Library,
115 Google Scholar) were deduplicated to 328, reduced to 95 after
title/abstract screening, and reduced to 30 after full-text review, each of
the 30 retained papers anchoring one distinct test-case representation.

Each representation was classified along eight dimensions (abstraction level,
V-model phase, underlying mechanism, representation language, formality,
testing paradigm, representation object, and usage context) and the 30
representations group into six broad paradigms, summarized in
Table~\ref{tab:paradigms}. A single running example, Requirement C of the
case-study SRS (\S9.2.1, \texttt{The support structure for communicating commands
must be reliable, with a uniform ACK/NAK protocol adopted across all systems.
Timeouts must be supported at approximately 500 msec.}), was instantiated
across all 30 representations as a worked catalog, so that what "the same
requirement, a different representation" actually looks like in practice is
concrete rather than asserted.

\section{The Three-Gate Framework}
\label{sec:framework}

Every generated suite passes through three gates in sequence, each with a
fixed, pre-registered threshold; thresholds below are exactly what the
pipeline implementation enforces, not an idealized or aspirational version of
the design. Table~\ref{tab:gates} summarizes the three gates before the
formulas and thresholds are given in full.

\midrule
Gate 1: RSS & $\geq 0.60$ & Is the chosen test-case representation actually suited to this requirement's kind of behaviour? \\

Gate 3: FSA + $M_g$ & $\geq 0.50$ & Does the suite cover the right clauses, including negative and boundary cases, with precise oracles and values grounded in the requirement text? \\

\textbf{Gate 1: Representational Suitability (RSS).} Before any test is
generated, the model must choose, or be offered, a representation for the
requirement at hand. RSS scores that choice heuristically:
\begin{equation}
\mathrm{RSS} = 0.40\,M_1 + 0.30\,M_2 + 0.15\,M_3 + 0.15\,M_4,
\end{equation}
where $M_1$ is concern alignment (does the representation match the kind of
property the requirement describes), $M_2$ is abstraction-level alignment,
$M_3$ penalizes unnecessary representational complexity (Occam's razor), and
$M_4$ scores whether the representation is one an LLM can plausibly generate
correctly. The weights $\{0.40, 0.30, 0.15, 0.15\}$ were set by expert
elicitation during design: $M_1$ receives the largest share because choosing
the wrong concern class (e.g., a state representation for a pure business
rule) is a structural mismatch that higher-weighted metrics cannot compensate
for; $M_2$ addresses the same issue one level of abstraction up. $M_3$ and
$M_4$ are secondary correctives. To check sensitivity to these weights, we varied each by
$\pm0.05$ (rescaling the others proportionally) for all 59 units
(754 unit-level perturbations; \texttt{tools/sensitivity.py}). The top-ranked
paradigm changed in 2.7\% of cases. The full paradigm ordering changed in 33\%
of cases, with mean Kendall's~\cite{kendall1938} $\tau=0.94$ against the baseline ordering, so
the top choice is robust but the order of lower-ranked paradigms is not.

An extended ten-metric form adds six further metrics,
$M_5$ to $M_{10}$ (Table~\ref{tab:extmetrics}), reweighted under six
system-profile-specific weight sets (standard, safety-critical,
rapid-prototyping, data-pipeline, distributed-concurrent,
interaction-heavy) for domain-specific weighting. Each requirement's
system profile is inferred automatically from its text; in the benchmark,
249 of 496 suites were scored under the standard profile and the
remaining 247 split across four of the other five (interaction-heavy 152,
data-pipeline 47, safety-critical 40, distributed-concurrent 8;
rapid-prototyping was never selected), so the extended metrics are
not a dormant option but an active part of roughly half the reported
results. \textbf{Threshold: RSS $\geq 0.60$}, with up to three re-picks
before the pipeline falls back to a default representation.

\textbf{Gate 2: Syntactic Form Validity (SFV).} Once a suite is generated,
SFV checks two things separately and blends them evenly:
\begin{equation}
\mathrm{SFV} = 0.5\,S_{\text{schema}} + 0.5\,S_{\text{repr}}.
\end{equation}
$S_{\text{schema}}$ is the fraction of canonical test cases that validate
against the pipeline's JSON schema, meaning every required field is
present, case ids are unique, and every \texttt{req\_id} the case cites
traces to a requirement actually present in the unit. $S_{\text{repr}}$ is
a family-specific syntax check of the representation artifact itself,
routed by the suite's \emph{actual} representation group rather than one
generic parser applied to everything. Gherkin suites are parsed with the
official Gherkin grammar~\cite{wynne2012cucumber} (0.0 on a parse error, 0.4 if it parses but
declares no \texttt{Scenario}, 0.8-1.0 depending on step density);
Programmatic/Code-level suites are checked with Python's \texttt{ast}
parser plus the presence of test functions and assertions;
Stateful/Transitions suites are scored on five structural signals
(declared states, an initial state, at least two transitions,
events/guards, and balanced brackets); Scenario/Behavioral suites that are
not Gherkin, such as use cases and user stories, are scored on four
signals (a named actor, a main flow, at least one alternative or
exception flow, and numbered steps); Concurrency/Interaction,
Logical/Combinatorial, and Formal/Symbolic/Contract suites each get an
analogous family-specific structural check (arrow and participant markers
for sequence diagrams, consistent column counts and separator rows for
decision tables, relational operators and matrix-like rows for symbolic
notations). A suite passes Gate 2 only if $S_{\text{schema}} = 1.0$
\emph{and} $S_{\text{repr}}$ separately clears a per-group threshold
(Table~\ref{tab:sfvthresh}); a perfect schema score cannot compensate for
a failing representation score, or vice versa. \textbf{Threshold: SFV
$\geq 0.60$} by default, tightened to $\geq 0.70$ for
Stateful/Transitions and Formal/Symbolic/Contract suites, and to $1.00$
for Programmatic/Code-level suites, since a syntax error there means the
suite does not run at all.

\textbf{Gate 3: Functional Semantic Adequacy with Groundedness (FSA+$M_g$).}
Suites that clear Gates 1 and 2 are reviewed by a 20B open-weight judge model along four
adequacy dimensions plus groundedness:
\begin{equation}
\mathrm{FSA} = w_c C_{\text{clause}} + w_n C_{\text{neg}} + w_o A_{\text{oracle}} + w_b C_{\text{bound}} + w_g M_g,
\end{equation}
with standard-profile weights $w_c=0.30$ (clause coverage), $w_n=0.20$
(negative-path coverage), $w_o=0.15$ (oracle assertiveness), $w_b=0.20$
(boundary-case coverage), $w_g=0.15$ (groundedness), and six system profiles
analogous to Gate 1. For the standard profile, each FSA component maps to ISO/IEC/IEEE 29119-4~\cite{iso29119_4}. Clause coverage reflects requirements-based testing~\cite{whalen2006requirements}, whose coverage items are atomic requirements (\S5.2.12); it receives the highest weight because an uncovered clause is an untested aspect of the requirement. Negative and boundary coverage receive equal secondary weights, since requirements-based tests are typically positive and negative cases require complementary techniques such as boundary value analysis (\S5.2.12.3, \S5.2.3). Oracle assertiveness and groundedness assess expected results~\cite{barr2015oracle}, which the standard requires to be derived from the test basis (\S5.1)~\cite{iso29119}; a value not traceable to the requirement violates this. The specific weights, in all profiles, are our design choices; as Section~\ref{sec:validity} shows, a low groundedness weight lets ungrounded suites pass, motivating a separate threshold. As with RSS, we varied each FSA weight by
$\pm0.05$ (others rescaled proportionally; \texttt{tools/sensitivity.py}).
Suite-level pass/fail at FSA $\geq 0.50$ changed in 3.6\% of decisions
(111 of 3{,}110). Rankings were not fully stable: the paradigm ordering changed
in 6 of 10 perturbations, but only through swaps of adjacent paradigms
(Kendall's $\tau\geq0.867$), and the best and worst paradigms were never displaced
by more than one rank. Groundedness itself is
\begin{equation}
M_g = 1 - \frac{H}{A},
\end{equation}
the fraction of asserted concrete values ($A$) that are \emph{not} traceable
to the source requirement text ($H$ = hallucinated~\cite{ji2023hallucination}). \textbf{Threshold: FSA
$\geq 0.50$.} Suites that fail Gate 3 are fed back for up to three
closed-loop repair attempts~\cite{shinn2023reflexion} before being recorded as a final failure. The
full pipeline is shown in Fig.~\ref{fig:pipeline}.

\textbf{Threshold rationale and design-document discrepancy.}
The thresholds RSS~$\geq 0.60$, SFV~$\geq 0.60$, FSA~$\geq 0.50$ were
chosen conservatively relative to the original design documents, which
specified SFV~$\geq 0.80$ and FSA~$\geq 0.75$. The thresholds were relaxed
so that enough suites reach Gate~3 to study the judge's behaviour; under the
implemented thresholds, 311 of 496 suites (63\%) reach Gate~3. The implemented thresholds therefore
reflect a deliberate trade-off: enough suites reach Gate~3 for comparative
analysis at the cost of a lower quality bar. Under the stricter
design-document thresholds, only 106 of the 311 judged suites would pass
Gate~3 (vs.\ 214 actual) and the benchmark findings would
rest on a substantially smaller sample. We flag this discrepancy explicitly
because a methods section that quietly followed the more demanding,
unimplemented thresholds would misrepresent the very results it reports,
an error of exactly the kind this paper argues the field should stop making
silently. All results in this paper reflect the implemented, looser
thresholds.

The judge prompt (\texttt{fsa\_judge.txt}) is the one most relevant to
Section~\ref{sec:validity}: it instructs the judge to decide, value by value,
whether a concrete number, name, or state asserted in the suite is actually
entailed by the requirement text, which is exactly the groundedness check
later found to disagree so often with what execution against real code shows.

\section{Experimental Setup}
\label{sec:setup}

\subsection{Model Selection}
Candidate models were narrowed from an initial pool of 65 through a
four-stage funnel: licensing/recency screening~\cite{liesenfeld2023opening,white2024mof} (65$\rightarrow$31$\rightarrow$29),
hardware feasibility by VRAM and context length (29$\rightarrow$22), capability
and benchmark screening (22$\rightarrow$16), and a final state-of-the-art
(SOTA)/diversity pass
(16$\rightarrow$14), yielding 12 open-weight models plus two closed-source
controls (GPT-4o, Claude 3.5 Sonnet) intended as reference points.

Of the 12 open-weight models, \textbf{10 completed the full benchmark}:
Llama-3.1-8B~\cite{grattafiori2024llama3}, Qwen2.5-Coder-7B, Qwen2.5-Coder-32B~\cite{hui2024qwen25coder}, Qwen3-30B-A3B~\cite{yang2025qwen3}, Gemma-3-27B~\cite{gemma2025gemma3},
CodeGemma-7B~\cite{codegemma2024}, DeepSeek-Coder-V2-Lite~\cite{deepseek2024coderv2}, Granite-4.1-8B~\cite{granite4}, Phi-3.5-mini, and
Phi-3.5-MoE~\cite{abdin2024phi3}. Phi-4-14B~\cite{abdin2024phi4} failed Gate 1 on every attempted unit (server errors
mid-generation) and is excluded from the comparative results; Llama-3.3-70B
and the two closed-source controls were not executed, for compute and cost
reasons. We also note that Gemma-3-27B and DeepSeek-Coder-V2-Lite completed
only a small fraction of the full unit set (7 and 6 suites respectively,
against 58 to 61 for the other eight models); their aggregate statistics
below should be read with correspondingly lower confidence.

\subsection{Case Studies}
Three SRS/implementation pairs were used, each with its generated tests later
compared against its real codebase (Section~\ref{sec:results}):
\begin{itemize}
\item \textbf{doorstop}: the requirements-management tool Doorstop~\cite{browning2014doorstop}, with
its own Python implementation. 13 requirements extracted; time-budgeting
restricted generation to 2 units, each run against 2 representations
(4 suites per model).
\item \textbf{ventilator}: an open-source ventilator control system with
its own SRS and software implementation. 151 requirements extracted; 21
units generated, one representation per unit.
\item \textbf{virtual\_clinic}: a clinic-management web application
(Django-based) with a PDF SRS~\cite{shah2018virtualclinic}. 251 requirements extracted; 36 units
generated, one representation per unit.
\end{itemize}
Across the three case studies and 10 executed models this yields
\textbf{496 test suites and 4{,}058 test cases} (40 doorstop, 170 ventilator,
286 virtual\_clinic suites).
The same extraction, judge, and executor model was used for every generator,
to avoid a model favouring its own family's outputs~\cite{panickssery2024selfpref}. This model is
\texttt{gpt-oss:20b}~\cite{openai2025gptoss}, OpenAI's open-weight 20B model, served through Ollama~\cite{ollama} on
our group's GPU server during the experiment window (September--October 2026);
it is from a different family than every open-weight subject under test. The
judge temperature was fixed at 0 (seed 42) for all calls. Test generation used
only the SRS text; the real implementation was opened only at the
execution/audit stage (Stage S6), after every suite had been frozen, to prevent
code leakage into generation.
\textbf{Execution pass criterion.} Generated tests were run with
\texttt{pytest}~\cite{pytest} against the real implementation. A test counts as \emph{passing}
only if \texttt{pytest} reports it as passed; failed, errored, and skipped tests
(including those the executor marked as not implemented or not automatable) are
not passes. Of the 315 doorstop tests, 2 passed, 63 failed, 51 errored, and 180
were skipped.

\section{Results II: Validity Checks}
\label{sec:validity}

Section~\ref{sec:results} reports what the three-gate pipeline says about
itself. This section checks those statements against evidence the pipeline
did not produce: real test execution, a code-grounded audit, and an
independent heuristic. All three checks were built into this study
specifically because we did not want to publish a benchmark leaderboard
without first asking how much the leaderboard's underlying scores can be
trusted.

\textbf{Execution agreement.} On doorstop, the one case study where generated
tests were actually executed against the real implementation rather than only
audited, the picture is stark: across the ten executed models, \textbf{only 2 of 315
generated tests passed} (63 failed, 51 errored, and 180 were skipped,
mostly as not implemented). Eight of ten models produced zero passing tests
out of 10 to 49 attempts each; the only passes were one each for
Qwen2.5-Coder-7B (1 of 25) and Qwen2.5-Coder-32B (1 of 33).
Gate-passing and real test-execution success are, on this evidence, close to
unrelated for this case study: a suite that clears Gates 1 through 3 is not
meaningfully more likely to run successfully against the real system than one
that does not. The one weak positive signal is a moderate correlation between
FSA and execution pass rate across the suites for which both are available
($\rho=0.433$, $n=15$, $p=0.11$, not significant), present but on a small sample, and far from
strong enough to license treating a high FSA score as evidence a suite will
execute correctly.

\textbf{Where the execution failures come from.} The pytest files actually run
in this check are not the generator's native-notation artifact; they are
written by the same executor model (\texttt{gpt-oss-20b}) from the canonical
JSON test case plus a retrieved, necessarily incomplete set of source
excerpts (Section~\ref{sec:setup}), a translation step with its own failure
mode, separate from Gate 3's semantic judgment. Of the 315 cases in the full
10-model doorstop run, 180 (57\%) never reached a pass/fail outcome at all:
the same executor model marked 136 \texttt{not\_implemented} and 44
\texttt{not\_automatable} before running anything, leaving 65 cases actually
executed, of which 2 passed, a 3\% pass rate among the cases the pipeline
itself judged executable. Of the 114 cases that did fail or error, the
executor's own three-way triage attributes 107 to \texttt{test\_bug} (the
generated/translated test is wrong) and only 7 to \texttt{code\_mismatch}
(the implementation disagrees with the requirement); the single most common
failure signature, 49 of the 114 (43\%), is a wrong-arity call into
doorstop's own API, for example \texttt{Document.new()} invoked without its
required \texttt{root} and \texttt{prefix} arguments. By the pipeline's own
account, most observed failures sit in test design or in this translation
step, not in doorstop's implementation; the near-zero pass rate reported
above should be read accordingly, as evidence against the generated tests
and their translation into runnable code, not primarily as a statement about
the subject system's correctness. This does not rescue gate-passing as a
signal, a suite that clears all three gates is still no more likely to
execute than one that does not, but it does change what the failure is
evidence of. We flag this triage itself as a single, unverified LLM
judgment, for the same reason the audit's 18\% agreement rate below counsels
caution about any single judgment in this pipeline. Manual inspection of the
two passing cases themselves adds a further caveat: both assertions are weak.
One checks only that \texttt{doorstop.cli} and \texttt{doorstop.core} exist as
attributes, never exercising the ``lightweight installation'' requirement it
targets; the other wraps the call in \texttt{pytest.raises(Exception)}, which
passes on any exception at all rather than checking that the specific,
informative error message the requirement calls for is shown. The already
near-zero positive signal should be read with this in mind.

\textbf{Audit agreement.} Because full execution was only feasible for
doorstop (ventilator and virtual\_clinic lack an automatable test harness in
this study), the other two case studies instead rely on an LLM-judge
\emph{code audit}~\cite{zhuo2024icescore,tong2024codejudge}: the same judge model is shown retrieved code excerpts and
asked, for each test case, to return one of four verdicts describing whether
the code's behaviour matches the test's expectation: \texttt{satisfied}, the
code does what the test expects; \texttt{violated}, the code implements the
feature but disagrees with the expectation; \texttt{not\_implemented}, the
feature is absent; or \texttt{unclear}, the retrieved excerpt is insufficient
to tell. (On doorstop, actually running a test and seeing it fail triggers a
separate, three-way triage of \emph{why} it failed, by the same judge model:
\texttt{code\_mismatch}, the implementation disagrees with the requirement;
\texttt{test\_bug}, the generated test itself is wrong; or
\texttt{spec\_ambiguous}, the requirement does not clearly settle the
question.) On the doorstop test cases that were both executed (passed or failed) and given a
satisfied or violated audit verdict ($n=11$), \textbf{the audit agrees with real
execution on only 2 of 11, i.e.\ 18\%} (95\% Wilson~\cite{wilson1927} CI: 5\%--48\%). We flag the small sample
prominently: a one-sample proportion test at $n=11$ has very low power, and
the true agreement rate could plausibly be as high as 52\% or as low as 2\%.
The directional conclusion, that the LLM audit is an unreliable execution
proxy, is supported by the data: all 11 of these tests failed on execution, yet the
audit judged 9 of them \texttt{satisfied}, consistent with the
judge's tendency toward optimistic correctness assessment noted in
\cite{zheng2023judging,wang2024notfair}. We nonetheless recommend that future work replicate
this check on a larger doorstop sample before treating 18\% as a precise
point estimate. This is the single most important caveat on every
audit-based result reported for ventilator and virtual\_clinic elsewhere in
this paper and in the underlying analysis report: audit mode should be read
as a weak, frequently-wrong proxy for ground truth, not a substitute for
execution. Separately, across all three case studies, the audit flagged 192
individual test cases as contradicting the real implementation, combining an
audit \texttt{violated} verdict with, on the executed doorstop suites, an
execution-triage \texttt{code\_mismatch} verdict; given the 18\% agreement
rate just reported, this combined count should be treated as a rough signal
requiring manual confirmation, not a verified defect count.

\textbf{Representation-choice agreement.} As noted in
Section~\ref{sec:results}, a model's own Gate-1 pick of representation agrees
with the independent RSS heuristic's top-3 recommendation only 21\% of the
time on average. Gate 1 is designed to make representation choice
accountable to an external standard precisely because LLMs left to choose
freely cluster onto a handful of familiar notations
(Section~\ref{sec:results}); the low agreement rate shows that accountability
mechanism and the models' own judgment are, in practice, measuring different
things, and a high Gate-1 pass rate should not be read as confirmation that
the chosen representation was actually well suited to the requirement.

\textbf{Groundedness as a systematically missed failure mode (RQ4).} 243 of
311 judged suites (78\%) assert at least one concrete value (a timeout, a count, a
threshold) that cannot be traced to the source requirement text~\cite{liu2024codehallucination} (mean 12.4
hallucinated values per affected suite; mean $M_g=0.46$ across all judged
suites). Because groundedness is one of five weighted FSA components
($w_g=0.15$), a suite can clear the FSA~$\geq 0.50$ threshold while being
substantially ungrounded, as long as its other four components score well.
We found 112 of 214 Gate-3-passing suites with $M_g<0.5$, suites the
pipeline reports as adequate despite asserting more hallucinated values than
grounded ones.

\textbf{Circularity caveat.} The groundedness scores reported above, and
therefore the 78\% figure, are themselves produced by the same LLM judge
whose reliability is called into question by the execution check. A judge that
over-optimistically reports suites as \texttt{grounded: true} would cause
us to \emph{undercount} hallucinated suites; the true proportion of suites
with at least one ungrounded value is likely no lower than 78\% and may be
substantially higher. This circularity does not invalidate the groundedness
finding, but it means the 78\% figure should be treated as a lower bound
rather than a precise estimate. This is precisely why we recommend promoting
groundedness to an independently thresholded gate verified by a secondary
mechanism (e.g., automated lexical entailment against the SRS text), rather
than relying solely on the same judge that produces FSA.

\textbf{Against the real implementation, directly.} Even setting execution
and audit reliability aside, the \emph{best-case} agreement between generated
tests and real requirement-level behaviour, measured as the share of SRS
requirements whose tests reach actually-implemented behaviour, is 54\%
(DeepSeek-Coder-V2-Lite, doorstop); the ceiling across every
model$\times$project pair in this study is just over half.

\textbf{Summary of Results I and II together.} The pipeline reports
both-gates pass rates of 25\% to 100\% depending on model and case study
(Table~\ref{tab:doorstop}), and a representation-paradigm effect that is
statistically significant if small (Section~\ref{sec:results}). Set against real
execution, real code behaviour, and an independent heuristic, each of those
signals shrinks: 18\% audit-execution agreement, 2 passing tests out of
315 attempted, 21\% representation-choice agreement, and roughly three quarters of judged suites carrying at least one hallucinated value. A three-gate, LLM-judged pipeline is not nothing: it is more structured and more falsifiable than a single similarity score, but on this evidence it is not yet a substitute for execution-grounded validation, and should not be reported as one.

\section{Threats to Validity}
\label{sec:threats}

\textbf{Single run per configuration.} Every model$\times$unit$\times$
representation combination was run once at temperature 0; the underlying
analysis explicitly notes that differences of a few FSA points between models
are within expected noise and should not be over-interpreted~\cite{arcuri2014hitchhiker}.

\textbf{Single judge model.} All semantic adequacy, groundedness, and code
audit judgments were made by one model (\texttt{gpt-oss-20b}). We chose a
model from a different family than every subject under test to reduce
self-preference bias, a judge limitation documented in prior LLM-as-judge
work~\cite{zheng2023judging,panickssery2024selfpref}, but we did not cross-validate its judgments against a
second judge model or human raters~\cite{ahmed2025annotation} beyond the audit-vs-execution check in
Section~\ref{sec:validity}, which itself shows that judge's reliability is
limited.

\textbf{Execution harness is itself LLM-written.} The runnable pytest files
checked in Section~\ref{sec:validity} are not hand-written adapters; they are
generated by the same executor model from the canonical test case and a
retrieved, necessarily incomplete set of source excerpts (Section~\ref{sec:setup}).
An execution failure can therefore originate in Gate 1 through 3 test design,
in this translation step, or in the subject implementation, and this study
cannot fully separate the three from execution results alone. The pipeline's
own triage (Section~\ref{sec:validity}) attributes most doorstop failures to
the test/translation side rather than the implementation, but that triage is
itself a single, unverified LLM judgment, not a result this paper
independently confirmed.

\textbf{Uneven execution coverage.} Real test execution was only feasible for
doorstop; ventilator and virtual\_clinic results rely on the audit proxy,
which Section~\ref{sec:validity} shows agrees with execution only 18\% of the
time on the one case study where both are available. Conclusions drawn from
ventilator/virtual\_clinic audit data alone should be read as provisional.

\textbf{Partial model coverage.} Gemma-3-27B and DeepSeek-Coder-V2-Lite
completed only 6 to 7 suites each, against 58 to 61 for the other eight executed
models; Phi-4-14B failed to pass Gate 1 on any attempted unit; Llama-3.3-70B
and both closed-source controls (GPT-4o, Claude 3.5 Sonnet) were not
executed. The 10-model comparison in this paper is therefore narrower than
the 14-model selection funnel that produced it, and entirely open-weight.

\textbf{Threshold sensitivity.} The implemented gate thresholds (RSS~$\geq 0.60$,
SFV~$\geq 0.60$, FSA~$\geq 0.50$) are looser than the design-document
values (SFV~$\geq 0.80$, FSA~$\geq 0.75$). Under the stricter thresholds,
106 of the 311 judged suites would pass Gate~3 (vs.\ 214 actual);
all 311 already have SFV above 0.80. The paradigm ranking of
Section~\ref{sec:results} was computed under the implemented thresholds only
and was not recomputed under the stricter ones. The absolute pass rates in Table~\ref{tab:doorstop} would
drop materially under the stricter thresholds and should be interpreted as
lower-bound quality estimates specific to the implemented configuration.

\textbf{Three case studies.} doorstop, ventilator, and virtual\_clinic differ
in size and domain but are three systems; generalizing findings here to SRS
documents of very different style, domain, or scale (\eg safety-critical
avionics specifications) should be done cautiously~\cite{wohlin2012experimentation}.

\section{Discussion}

The clearest actionable finding from Section~\ref{sec:results} is that
\emph{which representation a requirement is tested with matters more than
which model generates the test}, a result consistent with the motivating
premise of this paper's own taxonomy (Section~\ref{sec:taxonomy})~\cite{utting2012taxonomy}, and one
that argues for representation-aware tooling over simply swapping in a larger
or more code-specialized model.

The more consequential finding, from Section~\ref{sec:validity}, is that this
and plausibly other LLM-judge-based evaluation pipelines should not be
trusted to report correctness without an execution-grounded check built in
and reported alongside the gate scores. We did not find this gap by assuming
our framework was flawed; we found it by deliberately building the
cross-checks (execution comparison, code audit, independent heuristic) that a
pipeline reporting only its own gate scores would never surface on its own.
We think this is the more general lesson: any LLM-as-judge evaluation
pipeline for generated tests should report at least one such cross-check, not
only its own internal pass rates, and groundedness in particular is
well-suited to being promoted from a weighted component of a blended score to
an independently thresholded gate, given how cleanly it can hide inside a
passing FSA score (Section~\ref{sec:validity}).

\subsection{Representation Mapping Rules}
The 21\% agreement between a model's free Gate-1 choice and the independent
RSS heuristic (Section~\ref{sec:validity}) shows the two views of
``suitable representation'' are, at present, only loosely connected. We plan
to formalize explicit mapping rules from requirement dependency type (state,
interaction, data, concurrency, as used in the RSS heuristic itself) to a
short ranked list of representations, so that representation selection is
governed by a documented, inspectable rule set rather than left to either an
LLM's free choice or a keyword heuristic alone.

\subsection{Full Execution Coverage}
Real execution in this study was only feasible for doorstop; ventilator and
virtual\_clinic results rely on the weaker audit proxy, which
Section~\ref{sec:validity} shows agrees with execution only 18\% of the time
on the one case study where both are available. The next iteration of this
work builds an automatable execution harness for both remaining case studies,
so that the 18\% audit-execution agreement figure can either be confirmed as
a general property of this evaluation approach or shown to be specific to
doorstop.

\subsection{System-Level Test Generation}
\label{sec:sysleveltesting}
Every suite reported in this paper covers exactly one requirement unit, up
to 8 requirements drawn from a single SRS section, in isolation. Nothing in
the current framework exercises a flow that spans multiple units, a
dependency between two separately specified requirements, an environment or
component failure, or a quality attribute (latency, throughput, reliability)
that only manifests across the running system rather than inside one
function. Closing this gap is the most structurally different piece of
planned work, since it requires a ground-truth structure the current
unit-level canonical schema (Section~\ref{sec:framework}) does not provide:
an explicit coverage denominator at the system level, analogous to what
traceability already gives at the unit level.

We are evaluating two candidate ground-truth formats for this purpose, shown
in Fig.~\ref{fig:sysgt} and summarized below.

\textbf{Candidate 1: a structured, dimension-based schema.} Every test is one
cell addressed by a composite id, for example
\texttt{E2E.F01.web-ui.negative.add-duplicate}, decomposing into a flow, an
interface, an input class, and a name. Each cell appears in three places: a
core record (preconditions, steps with an expected result per step, test
data), a dimension-specific record (one of D1 end-to-end, D2 interaction
between two requirements, D3 environment or component failure, D4 a quality
attribute tested below, at, or above its threshold), and an inventory line
carrying the requirement references that cell covers. A sync rule, every
cell id appears exactly once in the core, once in its dimension, and once in
the inventory, makes system-level coverage mechanically checkable the same
way unit-level traceability already is in this paper's framework (a pilot
inventory built this way already holds 189 cells across the four dimensions).

\textbf{Candidate 2: an industrial, spreadsheet-style sheet.} A simpler
alternative closer to common ISO/IEC/IEEE 29119~\cite{iso29119} (the international software
testing standard) style test-case documentation: one row per test, with id,
name, requirement links, precondition, steps, expected result, postcondition,
and use case as columns, plus a separate methodology sheet classifying each
row as happy-path, negative, or boundary. This format is easier for a human
reviewer to read and already separates expected result from postcondition,
but it has no explicit coverage-item inventory or denominator, so
system-level coverage cannot be computed from it the way it can from
Candidate 1, and concrete test-data values are more often left as vague
placeholders.

We plan to pilot Candidate 1 first, since its explicit, checkable
denominator extends this paper's existing traceability methodology most
directly from the unit level to the system level, and to compare it against
Candidate 2 on reviewer readability and on whether the heavier structure
measurably improves coverage auditability in practice before committing to
either format for the full benchmark.

\section{Related Work}

\textbf{Classical and SBST test generation.}
Search-based software testing (SBST)~\cite{mcminn2004sbst} approaches such as EvoSuite~\cite{fraser2011evosuite}
and Randoop~\cite{pacheco2007randoop} evolve test suites against coverage or
mutation-based fitness functions without requiring a natural-language source.
Rojas~\etal~\cite{rojas2015combining} study the combination of multiple adequacy
criteria in a single SBST objective, motivating our multi-gate design. These
approaches produce executable tests but require compilable code stubs and do
not consume requirements text; this paper addresses the upstream,
requirement-driven generation step.

\textbf{LLM-based test generation.}
Tufano~\etal~\cite{tufano2022unit} establish a Transformer baseline for unit
test generation using focal-context embeddings. More recently,
Schafer~\etal~\cite{schafer2023empirical} empirically evaluate LLMs for unit
test generation across multiple models and find that model specialization and
size do not reliably predict test quality, consistent with our RQ1 findings.
Yuan~\etal~\cite{yuan2023chatgpt} evaluate ChatGPT-generated JUnit tests and
introduce execution-based quality checks, finding that many syntactically
valid LLM tests fail at runtime; our execution pass rates ($\leq$2/315)
are even lower, likely because we target requirement-to-test generation
(where no code stub is given) rather than code-to-test generation.
Siddiq~\etal~\cite{siddiq2023empirical} study LLM-generated test assertion
correctness specifically and find substantial hallucination in asserted
values, corroborating our groundedness finding.
TestGen-LLM~\cite{alshahwan2024testgenllm} augments existing test suites
using coverage feedback~\cite{lemieux2023codamosa,pizzorno2024coverup,chen2024chatunitest}; we complement this by studying whether LLM-generated
tests are adequate in the first place when generated from requirements.
For requirements-to-test specifically, Hossain~\etal~\cite{hossain2024llmreq}
generate test cases from natural-language requirements using LLMs and evaluate
with BLEU, precisely the approach this paper argues should be augmented with
execution-grounded checks.

\textbf{LLM-as-judge evaluation.}
The use of a second LLM to evaluate generated artefacts is surveyed in
Gu~\etal~\cite{gu2024judgesurvey}; our paper is, to our knowledge, the
first to measure the measurement-validity gap of an LLM judge specifically
in the test-generation context, via comparison against real execution.
Reflexion~\cite{shinn2023reflexion} applies LLM self-feedback to agentic
tasks; our closed-loop repair is structurally similar but targeted at
test-suite adequacy scores rather than task completion signals.
SWE-bench~\cite{jimenez2024swebench} and SWE-agent~\cite{yang2024sweagent}
share this paper's concern with evaluating LLM outputs against executable
ground truth rather than static references, in the issue-resolution setting.
Deng~\etal~\cite{deng2023llmfuzzer} use LLMs as zero-shot fuzzers~\cite{xia2024fuzz4all} with
execution-grounded evaluation, consistent with the direction we recommend.

\textbf{Test adequacy metrics.}
Inozemtseva \& Holmes~\cite{inozemtseva2014coverage} show that statement
coverage is a weak proxy for real fault-detection ability~\cite{zhu1997adequacy,just2014mutants}, a precursor to
this paper's argument that gate-pass rates are weak proxies for execution
correctness. Our oracle assertiveness component (FSA) is consistent with
the test oracle generation literature~\cite{dinella2022toga,kang2023libro} reviewed by
Barr~\etal~\cite{barr2015oracle}.

Model licensing and openness considerations in our model-selection funnel
draw on~\cite{liesenfeld2023opening,white2024mof}; the open-weight code models are from
families documented in~\cite{grattafiori2024llama3,hui2024qwen25coder,yang2025qwen3,gemma2025gemma3,codegemma2024,deepseek2024coderv2,abdin2024phi3,granite4}, with
general LLM background from~\cite{ouyang2022instructgpt}.

\section{Conclusion}

We set out to build a careful, multi-gate alternative to text-similarity
metrics for evaluating LLM-generated, requirement-derived test suites, and
benchmarked it across 10 models and three real SRS/implementation pairs. The
resulting comparative findings, that model size and code specialization do
not predict adequacy while representation choice does, are useful on their
own. But the paper's central result is that the pipeline's own gate-passing,
checked against real execution, a code audit, and an independent heuristic,
agrees with ground truth far less often than its pass rates alone would
suggest. We report this as a finding about the field's current direction, not
only about our own pipeline: as LLM-as-judge evaluation becomes the default
replacement for text-similarity metrics in test generation research, it needs
to be held to the same standard it was introduced to meet, with
execution-grounded validity checks reported as a matter of course rather than
as an afterthought.
